## What I fixed by hand

I am not hiding what this run hit. `ALL CHECKS PASSED` and a sweep of zeros are the end of the session. They are not a claim that the first attempt at each step was clean. I fixed the failures by hand so the session could finish. The same fixes landed in pull request [#101](https://github.com/TontoBlanco/grow-room-platform/pull/101), "Fix the Nov 7 Home Assistant migration session failures", merged 7 November 2026 at 5:45 PM MST, commit `56c95d87`. These four are that pull request's session failures.

1. The EKS restore init container. Image `public.ecr.aws/aws-cli/aws-cli:2.39.3` does not contain `openssl`, `tar`, or `gzip`. The container crashed first on `openssl`, then on `tar`. `charts/home-assistant/files/restore.sh` still skips a nonempty database, still refuses keys outside `ha-backups/` or containing `..`, and still downloads with checksum mode enabled. SHA-256 is now `sha256sum`, converted to the base64 string S3 returns as `ChecksumSHA256`. If `tar` or `gzip` is missing, the script installs them with `dnf`, then `yum`, then `microdnf`. Package-manager output goes to stderr so the status line stays JSON. Editing that script did not roll the pod. A ConfigMap volume does not change the pod template, so the session needed a manual restart. The deployment now checksums the scripts ConfigMap. Installing packages and extracting the archive also ran past the 600 second progress deadline, so `progressDeadlineSeconds` is 900. That matches the Helm wait and the `kubectl rollout` timeout.
2. Windows `kubectl cp` of the EKS backup. A destination like `C:\Users\...\Temp\ha-eks-....tar.gz` is treated as a remote spec because `C:` looks like a host. The copy now goes to a relative leaf, `ha-eks-<guid>.tar.gz`, and `Move-Item` puts that file in the temp directory. `kubectl cp` also printed `tar: removing leading '/' from member names` on stdout. PowerShell captured that warning as function output, so the returned key became an array. The `kubectl cp` line is piped to `Out-Null`, and the function returns only the key string.
3. The WSL restore `mv`. The plan used `bash -c` with `$1` and `$2`. Windows PowerShell 5.1 expanded those before bash started, so `mv` ran with no paths (`mv: missing file operand`). Those steps are now direct argument lists: `mv` of the live folder to `.previous`, then `mv` of staging onto the live folder. Rollback is `mv -T` of `.previous` back onto the live folder, so a leftover `.previous` is not moved inside a config directory that is still there.
4. An empty process exit code on `down`. `Do-Down` starts `terraform apply` of the destroy plan with `Start-Process -NoNewWindow -PassThru`. On Windows PowerShell 5.1 that process object often has an empty `ExitCode` after `WaitForExit`. The script treated the empty code as failure, threw `destroy failed (exit )` after `Apply complete!`, and never reached the leftover sweep. A missing exit code is now a warning, and the sweep still runs. A real non-zero exit code still throws.

The same pull request has a separate image-scan commit. It is not one of the four session failures above. The build job's Trivy gate failed on `zlib1g` in `python:3.12-slim`. Debian's fixed package is DSA-6613-1, which is what Trivy lists for CVE-2026-76844 and CVE-2026-85091. The Dockerfile upgrades `zlib1g` from `trixie-security` and does not pin the version. The Trivy severity, `ignore-unfixed`, and the exit code are unchanged.

The steps and the failure table, including what a declined prompt does, are on the [Phase 8 page](../aws-poc/PHASE8_HA_MIGRATION.md).
